## Review follow-up (post-review fix, applied by orchestrator)

Independent review found one blocking defect: `generateAgentCredential` computed `tokenHash = sha256Text(token)` — the SHA-256 of the 43-character base64url token **text**, while doc 15, the SQL verifier (`neon/migrations/20260910002000_content_agent_connections.sql` — `sha256` of the base64-decoded 32 bytes) and the live suite (`neon/tests/capabilities.test.ts`) all hash the **decoded 32 bytes**. A connection created through the UI would have registered a hash the verifier could never match (`invalid_capability` on first agent call), invisible to unit tests because both sides were consistently wrong.

Fix applied:

- `packages/content-core/src/digest.ts` gained `sha256Bytes(bytes)` (exported via `index.ts`); `connectionConfig.ts` now exposes `generateAgentSecretBytes()` (the raw 32 Web-Crypto bytes) and computes `tokenHash = await sha256Bytes(secretBytes)` over those exact bytes — never over the token text. The token and the hashed bytes are produced from one `generateAgentSecretBytes()` draw, so the decoded credential is guaranteed byte-identical to the hashed bytes.
- `connectionConfig.test.ts` updated: the invariant is now `tokenHash === sha256Bytes(base64url-decoded token)` (two tests, including an end-to-end decode-the-token-back guard), replacing the wrong `sha256Text(token)` assertion.
