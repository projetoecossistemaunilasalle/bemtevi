## Inventory

**Migration 4 — `neon/migrations/20260910003000_content_draft_publication.sql`**

- Private helpers (`content_private`, `SET search_path = ''`, UTC, fully qualified, no overloads/defaults, revoked from `public/anonymous/authenticated`), matching the doc-15 frozen signatures:
  - `preparation_json(public.content_publish_preparations)` — camelCase `PublicationPreparation` projection (`preparationId`, `draftId`, `generation`, `expectedRevision`, `digest`, `expiresAt`); never exposes the stored token hash.
  - `prepare_publish(uuid, bigint, bigint, text, text, text, uuid, uuid)` — validates the 64-hex digest and token-hash inputs (`invalid_input`), enforces the agent⇄connection parity, then follows the doc-15 lock order (draft `FOR UPDATE`, published `FOR SHARE`, before inserting the new preparation). Generation mismatch → `stale_generation` + `currentHead`; digest mismatch → `preparation_invalid`; `expectedRevision` must equal both the live revision and the draft baseRevision → otherwise `revision_conflict` + `currentRevision`. Preparation-UUID replay requires all bound fields/hash/actor identical and still pending/unexpired; matching expired replay → `preparation_expired`; anything else → `preparation_invalid`. No payload write.
  - `publish_draft(uuid, text, text, uuid, uuid)` — verifies the immutable actor/principal/connection binding and the raw 43-char base64url publish token (decoded, sha256 over the 32 decoded bytes, compared against the stored hash; the raw token never reaches a stored column). Published outcome replays the stored `PublishResult` even after preparation expiry (the wrapper reauthenticated, so capability expiry/revocation/admin removal already failed before this point); stale/expired rows never rebind (`preparation_invalid`). Pending expired → mark `expired`+`completed_at`, return `preparation_expired`. Draft generation/digest drift → mark `stale`, return `preparation_stale`. Live/base revision mismatch (including coexistence drift from legacy direct writes) fails closed → mark `stale`, return `revision_conflict` + `currentRevision`; the draft is preserved for explicit engineering reconciliation. Success: exactly one revision increment (`published_content` update with server timestamps, `published_by` = principal admin, `published_via_connection_id` = delegating connection or null), draft `base_revision` → new revision / `generation`+1 / actor attribution (payload/digest unchanged), and the exact `PublishResult` stored atomically with outcome/completed_at. The existing `archive_published_content()` trigger remains the **sole history writer**.
  - **Design note (verified against real Postgres):** `publish_draft` RETURNS the `Result<T>` envelope directly instead of raising domain codes through a wrapper catch block. A plpgsql block with an EXCEPTION clause is a subtransaction — catching a raised domain error would roll back the terminal-outcome mark made before it. Returning the error after the mark makes the mark commit with the request, exactly as doc 15 requires ("do not RAISE it away"). Unexpected SQL exceptions still propagate and roll back publication/history/draft/outcome together. Prepare keeps the raise/catch protocol (it makes no marks).
- Wrappers: `prepare_content_draft_publish(uuid, bigint, bigint, text, text)` and `publish_content_draft(uuid, text)` (admin: `is_admin()` + `auth.user_id()`, authorization before any data-bearing error); `agent_prepare_publish(uuid, text, uuid, bigint, bigint, text, text)` and `agent_publish_draft(uuid, text, uuid, text)` (anonymous gateway, reusing `content_private.authenticate_agent`; publish reauthenticates even on replay). Wrapper MESSAGE_TEXT handling splits a possible `;{json}` detail suffix before matching the frozen code (another smoke-caught defect: the raw MESSAGE_TEXT of `stale_generation;{...}` / `revision_conflict;{...}` includes the detail and would otherwise fail the known-code membership check and re-raise).
- Privileges: all functions revoked from `public/anonymous/authenticated`; admin wrappers granted to `authenticated` only; agent wrappers granted to `anonymous` only; no new table policies; legacy direct-publication privileges on `published_content` intentionally kept until cutover.

1. Wrappers compared the raw `MESSAGE_TEXT` (which carries the `;{json}` detail suffix) against the known-code list, so detailed domain errors were re-raised instead of returned — fixed with `split_part(v_err_code, ';', 1)`.
2. Catching a raised domain error inside a wrapper EXCEPTION block rolled back the terminal-outcome mark (plpgsql subtransaction semantics) — fixed by having `publish_draft` return the Result envelope directly so the mark commits.
3. Smoke-side only: a history-attribution expectation queried the wrong revision and `has_table_privilege` argument order (SQL was correct).
