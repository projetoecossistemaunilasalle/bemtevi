## Notes / issues for downstream tasks

- Operation/allowlist semantics mirror `packages/content-core` literally (doc 14); the V1 facade `src/dev-dashboard/ai/aiOperations.ts` was not inspected for permitted keys.
- SQL `assert_payload` uses a per-scope "storage" allowlist (add ∪ patch ∪ unset ∪ protected image keys) because drafts are initialized from live published payloads that legitimately contain legacy image fields; generic operations remain restricted by the literal add/patch/unset lists.
- Base64 canonicality is enforced via `encode(decode(x))` equality with newline stripping; this covers padded-canonical roundtrip and zero trailing bits (PG's decoder tolerates non-zero trailing bits, but re-encode then differs).
- `parsePayload` was not used to normalize the seeded publication in tests; the conformance base payload is inserted verbatim so SQL structural validation sees production-shaped data.
- DB-02/DB-03 own the remaining RPCs in the frozen catalog; `rpc-types.ts` already documents their arg/result shapes but no wrappers/helpers for them exist yet.
- The live suites define a minimal per-file harness contract (env + owner `pg` + Data API fetch). DB-04 should validate it against actual Neon Data API behavior (e.g. RPC route shape) and may refactor into its owned harness files.
