## Discharged obligations and findings

- **CC-2 (MCP-02) discharged:** the packed-artifact smoke invokes the **installed bin entry file directly** (`node <install>/node_modules/@bemtevi/content-mcp/dist/index.js`), never a `.bin` shim, and the exchange verifies installed-bin serving end to end (initialize → tools/list → dispatches → termination) in the recorded run.
- **New guard finding (recorded for the `src/index.ts` owner, see change control):** the bin guard compares `pathToFileURL(process.argv[1]).href` with `import.meta.url`. Node resolves the ESM entry to its **realpath**, while `argv[1]` keeps the invoked path — so when the package directory is reached through a symlink/junction the guard does not fire and the process exits 0 **silently without serving**. Empirically probed: under a `pnpm` install (`node_modules/@bemtevi/content-mcp` is a junction), direct entry invocation did NOT serve; invoking the entry through its resolved realpath DID serve; under the npm clean install used by the smoke the package directory is real, so direct invocation serves. This affects `pnpm`-layout installs and `.bin`-shim/`npx` invocation paths and belongs to the runtime owner (fix needs a filesystem-free realpath alternative — `node:fs` is architecture-forbidden in MCP runtime sources), hence change control rather than an MCP-04 edit.
- **Protocol-version evidence:** doc 04's "modern discovery uses 2026-07-28" corresponds to the SDK's modern era (`server/discover` + per-request `_meta` envelope). The installed SDK 2.0.0, with the SDK-default options the package is required to use, does not register `server/discover` (its served list contains only pre-2026-07-28 revisions) and advertises `LATEST_PROTOCOL_VERSION = '2025-11-25'`. Per the task instruction ("do NOT invent one; assert the server replies with a supported version"), the smoke and the compatibility test read the version constants from the installed/resolved SDK at runtime and assert the server replies with a supported version; both `2025-11-25` (modern-era latest initialize) and doc 04's legacy `2025-06-18` are exercised end to end.
- **201-op expectation reconciled truthfully:** the task text expected `invalid_operations` for a 201-operation batch. The actual stack rejects it earlier: the SDK `fromJsonSchema` schema (`maxItems: 200`) validation inside `tools/call` returns `{isError:true, content:[{text:'Input validation error: Invalid arguments for tool apply_operations: data/operations must NOT have more than 200 items'}]}` with **no** `structuredContent`, before any handler/RPC. The smoke asserts this observed behavior and additionally produces the exact `invalid_operations` envelope through a schema-valid single op that reaches the handler (`update` with empty `patch`/`unset` → content-core allowlists), plus the unknown-scope batch (schema enum rejection, no hang). All edit-dispatch outcomes are credential-free and hang-guarded.
