- `grants.test.ts` expectations aligned with the audited base SQL: legacy direct writes are granted to `authenticated` only (anonymous has SELECT only), and post-cutover SELECT survives for `anonymous`/`authenticated` (never granted to `public`).

**One cross-task SQL fix (change-control item for DB-01):** `neon/migrations/20260910001000_content_draft_operations.sql`, `check_flow_add_nodes` iterated `for v_node in select e from jsonb_each(p_nodes) e` — selecting the whole composite (key,value) and assigning it to a `jsonb` variable, which fails on any non-empty node map with `22P02 invalid input syntax for type json` ("Token \"(\" is invalid"). ## Live harness design

- Provisioning uses the frozen DB-04 CLI command shapes (verified present in pinned `4.14.6`: `projects get`, `branches get`, `branches create --expires-at --no-secrets`, `data-api get`, `data-api create --auth-provider neon_auth --db-schemas public` (no `--add-default-grants`), `env pull --service postgres/auth/data-api --file <temp>/.env`, `data-api refresh-schema`, `branches delete`), plus one additional read-only call, `neon connection-string <parent> --role-name neondb_owner``neon connection-string <parent> --role-name neondb_owner`, whose sole purpose is the mandated step-1 owner inspection of the parent (no mutation, no context change). Version gate `neon --version` must print exactly `4.14.6` before any mutation. Provisioning overall timeout 120 s; suite timeout 10 min (SIGKILL + exit 124).
- Before any branch is created, the parent owner connection (read-only `connection-string`) runs `to_regclass('public.published_content')`; a parent that already carries the editorial tables is refused (unit-tested in `harness.test.ts`).
- Disposable branch `bemtevi-v2-test-<uuid>`, one-hour expiry, created from the dedicated fixture parent; create response is asserted (id/name/parent); `env pull` output must identify the created branch via `NEON_BRANCH`; the create-returned branch id is the authoritative cleanup id.
- Data API inspect-or-create: `data-api get` is verified (`status active`, `db_schemas` exactly `["public"]`, `db_anon_role` anonymous); absent that, create without default grants.
- Migrations are applied through the temporary owner connection (`DATABASE_URL_UNPOOLED`), auth-user sync is awaited, `admin_users` is seeded for A/B only, a minimal `published_content` row (revision 42, `conformanceBasePayload`) is seeded, then `data-api refresh-schema` runs.
- Sign-ins: three verified principals plus the public anonymous JWT; JWT `role`/`sub` claims are verified and each principal's `sub` must equal the DB-resolved `neon_auth."user"` id.
- Pool warmup: the first request on a fresh Data API backend can resolve `auth.user_id()` before request-scoped claims are visible (observed as spurious `unauthorized`); the harness warms the pool sequentially and with concurrent bursts until a full burst is clean.
- Phase 1 runs all DB-01..03 suites serially (coexistence). The cutover artifact is then applied through the owner connection, `refresh-schema` runs, and grants.test.ts re-runs with `NEON_TEST_CUTOVER_APPLIED=true`. The per-phase `it.runIf` skips are the specified two-phase mechanism, not credential skips — every accumulated live case executes in exactly one phase (116 + 6 + shared = 118 test cases).
- Cleanup in `finally`: re-reads the branch and verifies project id, retained id/name and the `bemtevi-v2-test-` prefix before `branches delete`; removes only the verified process-owned temp dir; cleanup failure fails `check:db` with sanitized project/branch ids. Phase failures route through the same cleanup path (verified: a mid-run failure deleted its branch; leaked branches from earlier iterations were deleted manually).
